| R3 | ✅ **CLOSED 2026-09-05: both loops measured.** The title loop's cost was measured and the ship paced by it (§6.110); the flight loop's was measured and the NTSC-refresh constant replaced by a cost model (§6.114), which is the two-sentence answer §6.17 gave in September finally applied. Slice 2e's second acceptance half closed on it. **The instrument was built 2026-09-03**: **Cadence had no oracle, and running the question down changed it.** The premise of this row was that the original's loop ran as fast as the machine allowed and that nothing could measure it. The first half is now confirmed from the shipped binary rather than assumed, and the second half is answered. | Med | **High** | **Owner ruling 2026-09-03: count cycles.** Built the same day. `Cpu6502` accumulates cycles — a base count per opcode, the page-crossing penalty on the twenty-three indexed reads and nothing else, and two, three or four for a branch — so a main-loop iteration divided by the C64's clock (985,248 Hz PAL, 1,022,727 Hz NTSC) is a duration. **The finding that reshaped the row:** a scan of the assembled build for calls to `WSCAN`, the vertical-sync wait, finds exactly three — `DELAY`, `TT16+7` and `FREEZE`. The BBC and 6502SP builds call it from the flight loop; the C64 build does not. So the rate is not a setting to choose but a **consequence** to measure, and the timing model splits in two: the main loop is cycle-budgeted and free-running (it slows under load, as the original visibly does), while `DELAY`, `TT16` and `FREEZE` need a vertical-sync tick, defaulting to 50 Hz PAL and configurable because `wscan.asm` says the machine decides. | ✅ **The model is validated against real code, and the residual is named.** `TT54` hand-counted from the source comes to 66 cycles over 23 instructions and the model measures 66 over 23; `DORND` comes to 36 over 13 and measures 36 over 13. `DORND2`, one byte earlier at the `CLC`, costs 38 — the difference is asserted, which pins the model to a known two-cycle instruction. Six mutations run: four caught outright, one found a real gap (comparing the *opcode's* page instead of the address a branch resumes from, which differ only on a branch that itself straddles a page — now tested both directions), one provably equivalent. **What is still not validated is the number that matters**, because a main-loop iteration does not exist until phase 3. Two known omissions are documented on the counter itself: a trapped call costs nothing, so any figure for a routine that prints or plots is a lower bound; and nothing the VIC-II steals from the processor is modelled, which on a real machine is a further 5-10%. So the port will be measured-and-slightly-fast rather than measured, and that is a claim that survives being asked about. **Both measurements are now taken and in use (2026-09-05).** |
| R4 | **6502 semantics leak.** Carry/overflow reuse, sign-magnitude coordinates, self-modifying operands, stack-popping returns, BCD, and routines that fall through into the next one: any of these can be mistranslated and still *look* right. | High | High | Bit-exact integer model (ADR-002); the oracle tests every pure routine on exhaustive 8-bit inputs (ADR-003 §1); porting principles §4.4 (document each trick at the call site). | 🔥 **Realised once, 2026-09-03 (slice 1b-b), and caught in a minute.** The port of the sixteen-step long division restarted the carry flag on every loop step; the original threads it through, so that what falls out of the top of the quotient is shifted into the remainder on the next step. Both versions read as a rotate, a compare, a conditional subtract and two rotates, and **nothing about the wrong one looks wrong**. It failed on the first case swept, naming the routine, the iteration and both numbers. This is the exact defect class the row predicted, the mitigation caught it at the cost of one rebuild, and the fix carries a comment so it does not get simplified back. **Substantially de-risked 2026-09-03 (slice 1b-a).** Nine routines built on exactly the hazards this row names — carry chained between shifts and additions, sign-magnitude operands, a deliberate off-by-one that cancels against a set carry flag, a subtract-and-negate branch — matched the shipped code over **all 65,536 input pairs each**, with the addition swept over 200,000 cases and its edges pinned by hand. The approach works, and the cost per routine is now known: read it, port it, write one exhaustive comparison. What is *not* yet evidence is the harder material — self-modifying operands, routines that discard their return address, and the drawing code's fall-through chains are all still ahead. **First evidence, 2026-09-02 (slice 0c).** The generator is exactly this risk in miniature — a carry chained from a rotate into one addition and on into a second, with each half storing a byte its partner just read — and the ported version agreed with the interpreter on the returned byte, the previous byte, C, V and all four state bytes over 60,000 iterations and 8,192 first calls. One routine is not a trend, but the *harness* is now proven, which is what phase 1 was going to spend its first sitting establishing. The interpreter's own suite also handles the stack-popping-return case: a run that unwinds past its entry point is reported as completed rather than spinning to the budget. |
| R5 | **Hardware effects reproduced wrongly.** Sprites (scanner blips, crosshairs, Trumbles), the raster interrupt that recolours the dashboard mid-frame, multicolour cell constraints, and erase-by-EOR all produce pixels by mechanisms the port does not have. | Med | Med | Emulate by effect (§4.5): the canvas draws the same pixels. **Revised 2026-09-03**: with the emulator gone, the check is no longer a screenshot comparison but the oracle itself — the game's drawing routines write a bitmap into the 64 KB image, so a test decodes those bytes and compares pixel for pixel. Exact rather than eyeballed, and it reaches further than a screenshot did. | 🔥 **Realised 2026-09-03 (slice 1d-0), before any drawing code was written.** The mechanism this row calls "emulate by effect" had been designed against a canvas that could not hold the effect: ADR-002 §4's one-colour-index-per-pixel storage cannot express a `PIXEL` write, because the C64 build indexes `TWOS2` and three of its eight masks set one bit of one multicolour pixel and one of the next. Measured rather than argued (ADR-002 §7), and the canvas is now four planes matching the C64's own screen state, so the oracle check this row depends on is a byte compare rather than a translation. The row's original validation stands for 1d-a onward: the first drawing routine compared against the bitmap the shipped code produces. What the oracle still cannot judge is anything the VIC-II did *outside* the bitmap — sprite overlay and the mid-frame palette split — and those stay a matter of reading the hardware's behaviour carefully and saying so in the code. **Standing 2026-09-05:** the mid-frame palette split is modelled (`Canvas::SetDashboardShown`, §6.98) and the sprite overlay is not — `SIGHT` writes the registers and nothing draws them (§6.100). That is now an open ADR-005 §1 decision rather than a risk: where compositing lives decides whether it can be tested at all. |

| R10 | **Golden images are brittle.** A one-pixel change in a shared primitive invalidates dozens of goldens and tempts a blanket re-record. | Low | Med | Goldens are few and named for what they prove; a re-record needs a visual diff (`tools/golden_diff.py`) attached to the change; the oracle, not the golden, is the authority for anything it can reach. | ✅ **Met 2026-09-03 (slice 1d-c), and the mitigation came out stronger than designed.** There are two goldens and each is checked twice: the shipped routines draw the scene into the oracle, its memory is decoded into a `Canvas`, and the two resolved images are compared **pixel for pixel** — so the golden is not a picture anybody accepted by eye.
